What is Attributor?

Attributor is a scientific web platform dedicated to the attribution of molecular formulas from mass spectra. It combines a compute engine written in Rust and compiled to WebAssembly (Attribrustor), heavy processing executed outside the main thread, and a scientific interface built on a visual, interactive data-flow. Everything runs in your browser, with nothing to install: import your data, assemble your processing pipeline and explore the results.

Main features

⚡ Rust / WebAssembly compute

Numerical kernels compiled to WebAssembly process spectral data quickly, directly in the browser.

🧵 Non-blocking compute

Heavy operations run in dedicated workers, so the interface stays responsive even on very large datasets.

🧮 Adaptive compute pool

Tasks are distributed across several workers according to the browser capabilities, with a queue and a JavaScript fallback if needed.

🔗 Interactive data flow

Add nodes, move them and link the steps of your analysis. The pipeline runs, updates and clearly visualises how data propagates.

📈 Integrated WebGL rendering

Explore XY data in interactive WebGL plots designed to keep large datasets fluid while panning and zooming.

🔬 0D persistent homology

A topological analysis module detects sub- and superlevel structures, returns their births and deaths, and filters the original points with a classifier line.

📂 Flexible import

Load delimited text files with configurable separator and columns, or convert raw .raw files through the msConvert service.

💾 Portable sessions

Export and import the complete pipeline as JSON, with session versioning and faithful restoration of the data structures.

↩️ Risk-free experimentation

Undo and redo every action through a complete history, tune parameters and compare the results of your scenarios.

Technical documentation

This section is the reference for the Attributor processing nodes. For each node it documents its purpose, its inputs and outputs, the constraints it enforces, and the way its data is laid out in memory.

Global conventions

Wave data layout

A Wave is a typed-array container. Its dims property lists the size of each dimension, and degree is the number of dimensions. The core is stored non-interleaved: the first dimension is the fastest-varying axis. 

new Wave(pointCount, 2)   // 2D wave: dims = [pointCount, 2]

core = [ x0, x1, x2, ..., y0, y1, y2, ... ]

core[i]              // X of point i
core[pointCount + i]  // Y of point i
index(i, 0)          // X of point i
index(i, 1)          // Y of point i

This is the only supported layout for a 2D wave. Interleaved data such as [x0, y0, x1, y1, ...] is never produced and never expected.

A 1D wave is declared as new Wave(n) and its core is simply [y0, y1, ...].

Compute layer

  • Numerical kernels are written in Rust and compiled to WebAssembly.
  • Kernels run inside dedicated workers, never on the main thread.
  • Kernels exchange only flat Float64Array buffers — never arrays of objects or nested pairs.
  • Output buffers are transferred (zero-copy ownership transfer) back to the UI thread.
  • A JavaScript fallback implements the same semantics if WebAssembly or workers are unavailable.

Node reference

Persistent Homology 0D

Computes 0D persistent homology (H0) on a single input wave, then filters the original points with a classifier line through the origin. Births and deaths are computed in Rust, the default slope is derived from the persistence pairs, and the filtering itself is also performed in Rust.

Item Specification
Inputs 1 input — a single 1D or 2D wave.
required exactly one link on input 0
Outputs 1 output — the original points kept by the classifier, as a non-interleaved 2D wave [X…, Y…].
The birth/death pairs are internal: they feed the persistence diagram only.
Input layout 1D: [y0, y1, ...]  ·  2D: [x0, x1, ..., y0, y1, ...]
Parameters filtrationMode — sublevel or superlevel (default superlevel).
slope — classifier slope, strictly below 1. null means “not fitted yet”.
logLogAxes — logarithmic display of the persistence diagram.

Algorithm

  1. The kernel reads the Y block of the input core directly (no copy, no interleaving).
  2. For superlevel, points are activated by decreasing Y; for sublevel, by increasing Y. Ties are broken by increasing X.
  3. Union-find merges adjacent components as the filtration level changes.
  4. Each input point yields one persistence pair: a birth equal to its own Y, and a death recorded when its component merges. The surviving component keeps death = 0.
  5. Results are reordered by increasing X, so the output is always X-sorted.
  6. The default slope is computed from the pairs, clamped to [1e-9, 1 - 1e-12].
  7. The filter keeps every pair with death <= slope × birth, and returns the corresponding original points.

Interactive behaviour

  • The persistence diagram shows kept pairs in green and discarded pairs in grey, on a WebGL canvas.
  • The classifier line is an SVG overlay drawn through the origin: death = slope × birth.
  • Clicking the diagram places the classifier at that location and recomputes the filter.
  • Changing the slope never recomputes H0: only the classification kernel is re-run.

Error conditions

  • error more than one link connected to the node, or a link targeting a removed input.
  • floating no wave connected yet, or the connected value carries no usable wave.
  • fallback WebAssembly or workers unavailable: an equivalent JavaScript implementation is used.

Session behaviour

The classifier slope, its marker position and the filtration mode are serialised with the session and restored on reload, so a fitted slope is never silently recomputed. Legacy sessions are migrated automatically: the removed slope input and birth/death output are dropped, and the points output is remapped to output 0.

Data flow

input wave core
   → kernel: persistent_homology_0d_waves(mode, stride)
   → births, deaths, pointsX, pointsY, defaultSlope
   → kernel: classify_persistence_0d(slope)
   → keptPointsX, keptPointsY, keptCount
   → output wave [X…, Y…]
